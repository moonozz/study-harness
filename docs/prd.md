# 나만의 서비스 아카이브 PRD

> 게시물 링크에서 서비스를 발견하고, 내 용도에 맞게 정리하고, 필요할 때 다시 꺼내 쓰는 개인 아카이빙 서비스

- 버전: v0.1 — 하네스 설계 전 제품 요구사항 초안
- 작성일: 2026-10-11
- 서비스명: 나만의 서비스 아카이브 (가칭)
- 참고: 첨부 이미지의 PRD 필수 5블록 및 첨부 PRD 예시의 상세 구성
- 문서 성격: 사용자가 제안한 핵심 목표에 MVP 운영 정책을 더한 초안. 플랫폼·기술 스택·수치 목표는 확정 사항이 아닌 제안이다.

## 1. 하네스 설계를 위한 필수 5블록

### 1-1. 한 줄 정의

**나만의 서비스 아카이브는 유용한 도구를 수집하는 내가 게시물 링크를 공유하면, 그 안에 소개된 서비스의 이름·설명·URL을 추출하고 카테고리별로 저장해 필요할 때 찾아 쓰는 서비스다.**

### 1-2. 주요 사용자 1명

디자인·프런트엔드 구현·AI 도구 활용을 함께 하는 나.

SNS와 블로그에서 유용한 서비스 소개를 자주 발견하지만, 저장한 게시물이 여러 플랫폼에 흩어져 있다. 서비스 이름을 잊으면 게시물을 다시 찾기 어렵고, 한 게시물에 소개된 여러 도구를 직접 정리하는 데 지쳐 있다. 내가 필요한 것은 게시물 보관을 넘어, **실제로 사용할 서비스를 용도별로 다시 찾을 수 있는 개인 자료함**이다.

### 1-3. 사용자 시나리오 3개

**시나리오 A — 서비스 여러 개가 소개된 게시물 저장**

1. 유용한 도구 여러 개를 소개한 게시물 링크를 복사해 서비스에 붙여 넣는다.
2. 서비스가 게시물에서 도구별 이름·설명·URL·카테고리 후보를 추출한다.
3. 추출 결과를 확인하고, 필요한 항목을 선택하거나 잘못된 정보를 수정한다.
4. 저장하면 선택한 도구들이 각각의 카드로 아카이브에 추가된다.

**시나리오 B — 필요할 때 다시 찾기**

1. 작업 중 사용할 도구가 필요해 아카이브를 연다.
2. 기억나는 이름이나 용도 키워드를 검색하고 카테고리로 좁힌다.
3. 카드의 설명과 내가 남긴 메모를 확인한다.
4. 상세 화면에서 서비스 URL을 열어 사용한다.

**시나리오 C — 링크를 읽지 못한 경우에도 저장**

1. 게시물 링크를 입력했지만 로그인 제한 등으로 내용을 가져오지 못한다.
2. 화면 안내에 따라 게시물 본문을 직접 붙여 넣는다.
3. 붙여 넣은 내용에서 추출된 서비스들을 확인하고, 없는 URL은 직접 보완하거나 확인 필요로 남긴다.
4. 원하는 항목을 저장하고, 이후 상세 화면에서 정보를 수정한다.

### 1-4. 만들 화면 5개 — 이름만

1. 내 아카이브
2. 링크 추가
3. 추출 결과 확인
4. 서비스 상세
5. 카테고리 관리

### 1-5. 지켜야 할 것 / 안 할 것

**지켜야 할 것**

1. 게시물 하나에 여러 서비스가 있으면 각각 분리하고, 각 서비스에 원본 게시물과 추출 근거를 연결한다. 확인되지 않은 설명·URL은 사실처럼 채우지 않는다.
2. 내가 추출 결과를 확인·수정한 뒤 저장하며, 저장된 정보는 기본적으로 나만 접근한다.

**안 할 것**

1. MVP에서는 공개 커뮤니티, 타인과의 공유, 유료 판매 기능을 만들지 않는다.
2. 모든 SNS의 자동 수집, 로그인 제한 우회, 이미지·영상만으로 된 게시물의 자동 분석을 MVP 필수 기능으로 약속하지 않는다.

## 2. 배경과 해결할 문제

유용한 서비스 소개는 SNS, 블로그, 뉴스레터 등 여러 곳에서 발견된다. 하지만 플랫폼의 저장 기능은 게시물을 보관할 뿐, 그 안에 소개된 도구를 개별적으로 정리해 주지는 않는다.

현재의 불편함:

- 저장 위치와 게시물 제목은 기억나지 않고, 필요한 기능만 기억난다.
- 한 게시물에 여러 서비스가 소개되어도 게시물 단위로만 저장된다.
- 서비스 이름, 설명, 접속 URL을 직접 옮기는 일이 반복된다.
- 분류 기준이 없어 저장 자료가 많아질수록 탐색이 어려워진다.

해결 방향은 **게시물 → 개별 서비스 → 용도별 분류 → 재검색 → 실제 사용**의 흐름을 만드는 것이다. 원본 게시물은 출처로 유지하고, 아카이브의 기본 단위는 개별 서비스로 둔다.

## 3. 제품 비전과 목표

> 발견한 도구를 나중에 실제로 쓸 수 있는 개인 서비스 라이브러리로 바꾼다.

MVP 목표:

1. 링크 한 번 입력으로 여러 서비스 후보를 정리한다.
2. 사용자가 확인하고 고치는 시간을 줄이되, 사실 확인과 최종 선택권을 유지한다.
3. 이름을 잊어도 설명·카테고리·태그·메모로 다시 찾게 한다.
4. 자동 추출이 실패해도 본문 붙여 넣기와 직접 입력으로 저장을 끝낼 수 있게 한다.

수익화와 사용자 규모 확대는 초기 목표에 포함하지 않는다. 먼저 개인 사용에서 저장과 재탐색이 유용한지 검증한다.

## 4. 핵심 유저스토리

| ID | 사용자로서 원하는 것 | 기대하는 결과 |
| --- | --- | --- |
| US-01 | 게시물 링크 하나를 공유하고 싶다 | 소개된 서비스들을 각각의 저장 후보로 받는다 |
| US-02 | 이름·설명·URL이 맞는지 확인하고 싶다 | 원문 근거를 보고 수정하거나 제외한다 |
| US-03 | 내 기준으로 서비스를 분류하고 싶다 | 자동 제안된 카테고리와 태그를 바꾼다 |
| US-04 | 필요한 용도의 도구를 다시 찾고 싶다 | 검색과 필터로 저장한 서비스를 찾는다 |
| US-05 | 읽을 수 없는 게시물도 기록하고 싶다 | 본문을 붙여 넣거나 직접 등록한다 |
| US-06 | 같은 도구를 여러 번 정리하고 싶지 않다 | 기존 항목을 확인하고 새 출처를 연결한다 |

## 5. 핵심 정보 구조와 화면 역할

| 화면 | 목적 | 주요 정보와 행동 |
| --- | --- | --- |
| 내 아카이브 | 저장한 서비스를 다시 찾기 | 서비스 카드, 검색, 카테고리·태그 필터, 즐겨찾기, 정렬, 링크 추가 |
| 링크 추가 | 추출을 시작하기 | 게시물 URL 입력, 본문 붙여 넣기, 처리 상태, 실패 시 대안 |
| 추출 결과 확인 | 저장할 정보를 확정하기 | 서비스별 후보 카드, 근거, 확인 필요 표시, 수정·선택·제외, 중복 검토, 저장 |
| 서비스 상세 | 도구를 사용하고 관리하기 | 이름, 설명, 서비스 URL, 카테고리, 태그, 메모, 원본 출처, 수정·삭제·즐겨찾기 |
| 카테고리 관리 | 내 분류 체계 유지하기 | 카테고리 추가·이름 변경·삭제, 연결된 서비스 수 |

직접 등록과 편집은 링크 추가·추출 결과·상세 화면의 모드 또는 모달로 제공한다. 초기에는 별도 화면을 늘리지 않는다. 공개 배포 시 필요한 로그인은 접근 진입 과정으로 별도 구현한다.

## 6. 기능 요구사항

### 6-1. 링크 입력과 콘텐츠 수집

- 한 번에 게시물 URL 1개를 입력한다.
- HTTP/HTTPS URL 형식을 검증하고, 잘못된 입력은 수집 전에 안내한다.
- 접근 가능한 공개 웹페이지의 본문과 링크를 수집한다. 초기 지원 범위는 실제 샘플로 확인한 텍스트 중심 페이지로 제한한다.
- SNS 링크는 접근 가능 여부에 따라 처리하며, 로그인·접근 제한이 있으면 실패 사유와 본문 붙여 넣기를 제공한다.
- 요청한 URL과 최종 접근 URL을 함께 기록한다.
- 본문 붙여 넣기 모드에서는 원본 URL을 선택적으로 연결한다. 직접 등록도 가능해야 한다.
- 진행 중에는 상태를 표시하고, 중복 제출을 막는다. 화면을 떠나도 저장된 작업 상태를 다시 확인할 수 있게 한다.

### 6-2. 서비스별 정보 추출

게시물에서 소개된 서비스마다 다음 필드를 만든다.

| 필드 | 추출 및 저장 규칙 |
| --- | --- |
| 서비스명 | 원문에서 식별된 제품·서비스 이름. 저장 시 필수 |
| 서비스 설명 | 원문에 근거한 한국어 1~3문장 요약. 저장 시 필수이며 사용자 보완 가능 |
| 서비스 URL | 원문 링크나 그 링크의 검증된 목적지. 없거나 불명확하면 비워 두고 확인 필요 표시 |
| 카테고리 | 허용된 목록에서 대표 카테고리 1개 제안 |
| 태그 | 용도와 기능 중심으로 0~5개 제안 |
| 추출 근거 | 이름·설명에 대한 짧은 원문 구절과 URL 발견 위치 |
| 확인 상태 | 사용자가 확인할 부분과 그 이유 |

정책:

1. 게시물에 소개된 서비스가 N개이면 서비스 후보 N개를 만든다. 같은 서비스가 반복 언급되면 후보 하나로 묶는다.
2. 작성자, 광고 배너, 일반 문구를 서비스로 저장하지 않는다.
3. 서비스 URL과 원본 게시물 URL을 다른 필드로 관리한다.
4. 이름만으로 공식 도메인을 추측해 채우지 않는다. 외부 검색을 통한 URL 보완은 후속 기능으로 둔다.
5. 기사·추천 목록·제휴 링크 등 공식 서비스 URL인지 불명확하면 사용자가 확인할 수 있게 표시한다.
6. 서비스가 발견되지 않으면 빈 결과의 이유와 직접 등록 버튼을 제공한다.
7. 자동 생성된 정보와 사용자가 수정한 정보를 구분하며, 저장 후 재추출이 사용자 수정값을 덮어쓰지 않는다.

### 6-3. 결과 확인과 저장

- 후보별 선택·선택 해제 및 전체 선택을 제공한다.
- 이름·설명·URL·카테고리·태그를 저장 전에 편집할 수 있다.
- 각 후보에 원본 게시물과 추출 근거를 보여준다.
- URL이 없어도 이름과 설명을 입력하면 저장할 수 있다. 해당 카드에는 `URL 확인 필요`를 표시하고 서비스 열기 버튼은 비활성화한다.
- 선택한 후보를 한 번의 저장으로 처리한다. 후보별 성공·실패를 보여주고 실패 항목만 재시도할 수 있다.
- 작업과 후보의 고유 ID로 중복 저장을 막는다. 저장 완료 후 재클릭·재시도가 같은 항목을 추가 생성하지 않아야 한다.

### 6-4. 카테고리와 태그

카테고리는 큰 용도, 태그는 여러 세부 속성을 표현한다.

초기 카테고리 제안:

| 카테고리 | 포함할 용도의 예 |
| --- | --- |
| 디자인·프로토타이핑 | UI 디자인, 디자인 시스템, 화면 설계 |
| 개발·배포 | 코드 작성, 테스트, 웹사이트 구축, 호스팅 |
| 자동화·연동 | 반복 업무 자동화, 앱 연결, 워크플로 |
| 콘텐츠 제작 | 이미지·영상·음성·글 제작 |
| 생산성·협업 | 문서, 메모, 일정, 팀 협업 |
| 리서치·데이터 | 정보 탐색, 자료 분석, 데이터 시각화 |
| 미분류 | 용도가 불명확하거나 기존 분류에 맞지 않는 경우 |

- 서비스마다 대표 카테고리 1개와 복수 태그를 둔다.
- 여러 기능을 제공하는 서비스는 게시물에서 소개된 주요 용도를 대표 카테고리로 제안한다.
- AI 사용 여부는 `AI` 태그로 표현한다. 사용자가 원하면 별도 카테고리를 만들 수 있다.
- 자동 분류는 기존 카테고리를 사용하고 새 카테고리를 임의로 생성하지 않는다.
- 카테고리는 추가·이름 변경·삭제할 수 있다. 삭제 시 연결된 서비스는 미분류로 이동하며 서비스 자체는 삭제하지 않는다.
- 미분류는 기본 카테고리로 유지한다. 태그는 저장·편집 시 추가하거나 제거한다.

### 6-5. 검색과 탐색

- 서비스명·설명·태그·사용자 메모를 대상으로 키워드 검색한다.
- 한글·영문 검색을 지원하며 영문 대소문자는 구분하지 않는다.
- MVP 검색은 부분 문자열 일치로 시작한다. 의미 검색·자연어 추천은 후속 범위다.
- 카테고리, 태그, 즐겨찾기로 필터링한다. 서로 다른 필터 조건은 AND로 조합한다.
- 기본 정렬은 최근 저장순이며 이름순 정렬도 제공한다.
- 검색 결과가 없으면 검색어 수정·필터 초기화를 안내한다.
- 카드에는 이름·짧은 설명·카테고리·태그·URL 확인 상태를 표시한다.

### 6-6. 상세 관리와 중복 처리

- 저장 후에도 서비스 정보를 수정하고 개인 메모를 작성한다.
- 즐겨찾기 설정·해제와 삭제를 제공한다. 삭제는 확인 절차를 거친다.
- 동일한 정규화 서비스 URL은 강한 중복 후보로 표시한다. 이름만 같은 경우는 약한 중복 후보로 표시하고 자동 병합하지 않는다.
- URL 정규화는 호스트 대소문자·기본 포트·명확한 추적 파라미터 등을 처리하되, 의미 있는 경로·쿼리는 보존한다. 같은 도메인의 다른 제품을 일괄 병합하지 않는다.
- 사용자가 `기존 서비스에 출처 추가` 또는 `별도 서비스로 저장`을 선택한다.
- 출처 추가는 기존 이름·설명·메모를 덮어쓰지 않는다. 같은 출처의 재연결도 중복 생성하지 않는다.
- 결과 화면 안에서 같은 서비스로 판단된 후보들은 저장 전에 묶어 검토할 수 있어야 한다.

## 7. 처리 상태와 예외 흐름

| 상황 | 시스템 동작 | 사용자가 할 수 있는 일 |
| --- | --- | --- |
| 링크 형식 오류 | 입력 오류 표시 | URL 수정 |
| 본문 수집 중 | 처리 상태 표시 | 완료 대기 또는 화면 이탈 |
| 수집·추출 완료 | 후보 목록 표시 | 확인·수정·저장 |
| 로그인 제한·접근 차단 | 실패 사유 표시 | 본문 붙여 넣기 또는 직접 등록 |
| 이미지·영상 중심 게시물 | 텍스트 부족 안내 | 설명을 직접 입력 |
| 서비스 0개 발견 | 서비스 없음 결과 | 다른 본문 입력 또는 직접 등록 |
| URL 누락·불명확 | 후보에 확인 필요 표시 | URL 보완 또는 미확인 상태로 저장 |
| 일부 서비스만 추출 | 수집·추출 한계 표시 | 누락 후보를 직접 추가 |
| 저장된 서비스와 중복 | 기존 서비스 정보 표시 | 출처 추가 또는 별도 저장 |
| 시간 초과·일시 오류 | 입력과 현재 결과 유지 | 재시도 또는 본문 붙여 넣기 |
| 일부 저장 실패 | 항목별 저장 결과 유지 | 실패 항목만 재시도 |

작업 상태는 `대기 → 수집 중 → 추출 중 → 검토 가능 → 저장 완료`를 기본으로 한다. 접근 불가·시간 초과·추출 오류는 실패 사유와 함께 기록한다. 일부 저장은 `일부 저장` 상태로 남고, 서비스 미발견은 실패와 구분해 표시한다.

## 8. 데이터 모델 초안

개별 서비스와 출처 게시물은 다대다 관계다. 같은 서비스가 여러 게시물에서 소개될 수 있고, 게시물 하나가 여러 서비스를 소개할 수 있다.

| 객체 | 주요 필드 | 역할 |
| --- | --- | --- |
| User | id, created_at | 개인 소유권 기준 |
| SourcePost | id, owner_id, input_url?, resolved_url?, title?, input_type, fetched_at? | 원본 출처. 직접 입력은 URL 없이도 가능 |
| ImportJob | id, owner_id, source_post_id, status, error_code?, attempt_count, created_at, completed_at? | 수집·추출 작업 및 재시도 상태 |
| ExtractionCandidate | id, job_id, extracted_name, extracted_description, extracted_url?, proposed_category_id, proposed_tags, evidence, review_flags, edited_values, decision, saved_service_id? | 자동 추출값과 사용자 확정값, 저장 여부 |
| Service | id, owner_id, name, description, service_url?, normalized_url?, url_status, category_id, tags, memo, is_favorite, created_at, updated_at | 아카이브의 기본 저장 단위 |
| ServiceSource | id, service_id, source_post_id, candidate_id?, evidence_excerpt?, created_at | 서비스와 출처의 연결 |
| Category | id, owner_id, name, is_default, sort_order | 사용자 분류 체계 |

필드 정책:

- `input_type`: link / pasted_text / manual.
- `url_status`: source_link / user_provided / needs_review / missing. 원문에서 발견했다는 사실이 공식 URL 검증을 뜻하지 않는다.
- 후보 `decision`: pending / save_new / attach_source / skip.
- 서비스명·설명은 저장 시 필수, 서비스 URL은 선택이다.
- 사용자 메모는 원문 요약과 분리한다.
- 재시도마다 작업 시도 정보를 남기되, 후보 저장 식별자로 동일 후보의 서비스 중복 생성을 막는다.
- 원문 전체와 붙여 넣은 본문은 처리·검토에 필요한 기간에만 보관한다. 초안 정책은 작업 종료 후 7일 내 삭제이며, 서비스별 짧은 근거와 출처는 유지한다.
- 서비스 삭제 시 연결 정보도 삭제한다. 다른 서비스가 참조하는 원본 출처는 유지한다.

## 9. 권한과 제품 조건

- 초기 사용자는 나 1명이며 저장 데이터는 비공개다.
- 외부에서 접근 가능한 서비스로 배포한다면 인증과 서버 측 소유권 검증을 필수로 둔다. 숨겨진 URL만으로 접근을 제한하지 않는다.
- 외부 게시물은 분석 대상 데이터로 취급한다. 게시물에 적힌 명령문이 시스템 동작이나 도구 권한을 바꿀 수 없어야 한다.
- URL 수집은 HTTP/HTTPS의 공개 목적지로 제한하고, 내부 주소·로컬 주소·비지원 스킴을 차단한다. 리디렉션 목적지도 같은 기준으로 검사한다.
- 이름·설명 등 외부 텍스트를 실행 가능한 HTML로 렌더링하지 않는다.
- 원본 전문을 공개 재배포하지 않고, 필요한 요약·짧은 근거·출처 링크만 아카이브에 유지한다.
- 실패해도 이미 저장된 서비스나 사용자가 수정한 내용이 유실되지 않아야 한다.

## 10. MVP 범위

### 반드시 포함

1. 개인 전용 아카이브와 지속 저장.
2. 링크 1개 입력 및 공개 텍스트 페이지 수집.
3. 여러 서비스의 이름·설명·URL 후보 추출.
4. 카테고리·태그 제안 및 사용자 수정.
5. 추출 결과 확인·선택 저장·중복 출처 연결.
6. 본문 붙여 넣기 및 수동 등록.
7. 키워드 검색·필터·정렬.
8. 상세 조회·수정·메모·즐겨찾기·삭제.
9. 카테고리 관리와 명확한 실패·재시도 흐름.
10. 인증이 필요한 배포 환경에서 개인 접근 제한.

### MVP 제외

- 모바일 네이티브 앱과 OS 공유 메뉴 직접 연동. 초기의 링크 공유는 웹 입력창 붙여 넣기로 정의한다.
- 브라우저 확장, 메신저 봇, SNS 계정 자동 동기화.
- 이미지 OCR, 영상·음성 분석, 로그인 제한 우회.
- 자연어·의미 검색, 자동 추천, 서비스 가격·기능의 지속 모니터링.
- 공개 공유, 다중 사용자 협업, 결제·구독·마켓.
- 대량 링크 일괄 처리 및 외부 검색을 통한 공식 URL 자동 보완.

## 11. 성공 지표와 수용 기준

아래 수치는 MVP 검증을 위한 제안 목표다. 지원 페이지와 정답을 미리 지정한 샘플로 측정하며 모든 SNS에 대한 보장으로 해석하지 않는다.

| 지표 | 정의 | 제안 목표 |
| --- | --- | --- |
| 서비스 추출 재현율 | 정답 서비스 중 올바르게 발견한 서비스 비율 | 90% 이상 |
| 서비스 추출 정밀도 | 전체 추출 후보 중 실제 소개된 서비스 비율 | 95% 이상 |
| 근거 없는 URL 생성 | 원문·확인된 링크에 없는 URL을 자동으로 확정한 건수 | 0건 |
| 수정 부담 | 서비스명·설명을 고쳐야 저장 가능한 후보 비율 | 20% 이하 |
| 재탐색 시간 | 저장한 서비스 50개 중 지정한 도구를 찾는 데 걸린 시간 | 30초 이내 |
| 결과 제공 시간 | 지원 공개 페이지 입력부터 검토 가능까지 걸린 시간 | 90%의 작업이 30초 이내 |
| 재시도 중복 | 같은 후보의 저장 재시도로 새 서비스가 중복 생성된 건수 | 0건 |

핵심 수용 시나리오:

| ID | 입력·행동 | 통과 조건 |
| --- | --- | --- |
| AC-01 | 서로 다른 서비스 3개가 있는 지원 게시물 | 각 서비스 후보가 생성되고 선택한 항목만 저장된다 |
| AC-02 | 서비스 이름·설명은 있지만 URL이 없는 본문 | URL을 만들어 내지 않고 미확인 상태로 저장할 수 있다 |
| AC-03 | 로그인 제한 게시물 | 제한 사유를 보여주고 본문 붙여 넣기로 저장까지 진행된다 |
| AC-04 | 기존 서비스와 동일 URL의 새 게시물 | 중복을 알리고 기존 정보 보존 및 새 출처 연결이 가능하다 |
| AC-05 | 설명의 용도 키워드 검색과 카테고리 필터 | 두 조건에 맞는 서비스만 표시된다 |
| AC-06 | 추출된 설명과 카테고리를 수정한 뒤 저장 | 사용자 수정값이 상세 화면과 검색에 반영된다 |
| AC-07 | 후보 여러 개 저장 중 일부 실패 후 재시도 | 성공 항목은 중복되지 않고 실패 항목을 이어서 저장한다 |
| AC-08 | 카테고리 삭제 | 연결 서비스가 미분류로 이동하며 정보는 유지된다 |
| AC-09 | 수집 본문에 시스템 명령처럼 보이는 문구 포함 | 문구가 도구 실행이나 출력 규칙을 바꾸지 않는다 |
| AC-10 | 인증 없는 데이터 조회 요청 | 개인 서비스 목록·상세·수정 API 접근이 차단된다 |

첫 검증용 샘플은 20개를 제안한다: 단일 서비스 5개, 복수 서비스 5개, URL 누락·중복 4개, 접근 제한 3개, 서비스 없음·텍스트 부족 3개. 추출 품질은 정답을 구성할 수 있는 텍스트 샘플에서, 예외 처리는 나머지 샘플에서 평가한다.

이 문서는 제품 요구사항을 정의한다. 에이전트 구성·도구 선택·프롬프트·기술 스택은 다음 단계에서 결정한다.

| 작업 단위 | 입력 | 출력 | 검증·중단 기준 |
| --- | --- | --- | --- |
| 콘텐츠 수집 | 게시물 URL 또는 붙여 넣은 본문 | 본문, 발견 링크, 출처, 수집 상태 | 접근 불가와 빈 본문 구분; 대상 주소·시간·크기 제한 |
| 서비스 추출 | 수집 본문과 링크 | 구조화된 서비스 후보 및 근거 | 출력 스키마 검증; 근거 없는 URL 확정 금지 |

| 중복 확인 | 사용자 확정 후보와 기존 저장 항목 | 중복 후보와 비교 정보 | 이름만으로 자동 병합 금지 |
| 저장 | 사용자 선택·수정 결과 | 서비스·출처 연결 및 항목별 결과 | 소유권 검증; 후보 단위 중복 저장 방지 |
| 검색 | 키워드와 필터 | 저장 서비스 목록 | 사용자 소유 데이터 안에서만 조회 |

하네스에서 정할 내용:

- 추출 출력 스키마와 필수 필드 검증 방식.
- 수집 실패와 모델 출력 오류의 재시도 횟수·시간·비용 한도.
- 사용자 검토를 요청하는 조건과 확인 필요 표시의 기준.
- 작업별 상태 저장 및 중단 후 복구 방식.
- 원문 입력과 내부 지시의 분리, 수집·저장 도구의 권한 범위.
- 대표 샘플에 대한 평가 방법과 회귀 검증 기준.

이 작업 단위들은 반드시 각각 별도 에이전트로 구현할 필요는 없다. 제품의 처리 책임과 검증 지점을 먼저 명확히 하기 위한 구분이다.

## 14. 가정과 후속 확인 사항

초안을 작성하기 위한 가정:

1. 개인용 반응형 웹서비스로 시작한다.
2. 입력은 게시물 링크 붙여 넣기가 기본이며, 모바일 공유 메뉴 연결은 후속 기능이다.
3. 자동 저장보다 검토 후 저장을 기본으로 한다.
4. 서비스 URL이 누락돼도 아카이빙을 허용한다.
5. 가격·무료 여부·계정 필요 여부는 정확성이 별도 검증되어야 하므로 자동 추출 필수 필드에서 제외한다.

구현 전에 확인할 사항:

- 가장 자주 공유할 게시물 플랫폼과 실제 대표 링크는 무엇인가?
- 초기에 제안한 카테고리가 내 탐색 기준과 맞는가?
- 주로 PC에서 정리하는가, 모바일에서 바로 저장하는가?
- 서비스 URL 확인을 매번 하고 싶은가, 미확인 상태를 모아 나중에 보완하고 싶은가?
- 사용할 모델·호스팅·인증·저장 방식과 허용 가능한 월 운영비는 어느 정도인가?

이 항목들은 문서의 미완성 구간이 아니라, 실제 수집 가능 범위와 하네스 실행 정책을 확정하기 위한 다음 결정 사항이다.

## 15. 제출물과 완료 기준

MVP 산출물:

1. 5개 핵심 화면과 사용자 시나리오 3개의 연결 흐름.
2. 서비스·출처·후보·작업 상태를 구분한 데이터 구조.
3. 수집·추출·분류·중복 확인·저장 정책.
4. 지원 게시물 범위와 실패 시 수동 입력 경로.
5. 수용 시나리오 검증 결과와 남은 한계.

**완료 기준은 내가 링크를 넣어 개별 서비스로 정리하고, 나중에 용도로 검색해 실제 서비스에 다시 접근하는 흐름을 끝까지 수행할 수 있는 것이다.**
