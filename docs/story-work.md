# story-work.md

## 실험의 성격

개인 서비스 아카이브의 PRD와 story-service를 설계·구현 작업으로 풀어낸 이야기다. 사용자가 제공한 실제 작업 방식인 **uibowl 레퍼런스 수집 → 분석 → 화면 설계 → 키스크린 → 내부 협의 → 토큰·컴포넌트와 전체 화면 → 가이드 검토**를 중심으로 기존 작업 계획을 수정했다.

서비스의 핵심은 게시물 링크나 본문에서 개별 서비스의 이름·설명·URL을 추출하고, 미리 준비한 카테고리·태그 기준으로 확인·수정한 뒤 저장해 다시 찾는 것이다.

이 문서는 **실제 작업 방식에 기반한 프로젝트 실행 계획**이다. 레퍼런스 수집·Figma 제작·관계자 컨펌·구현·테스트를 이미 수행했다는 기록은 아니다. 나는 서비스 사용자·디자이너·프런트엔드 개발자 역할을 맡고, 분석 방향과 컨셉은 내부 관계자들과 확인한다. 관계자의 구체적인 이름·역할·최종 승인자는 착수 시 정한다.

## 작업 이야기

| 단계 | 누가 무엇을 하는가 | 산출물 | 판단·협업 지점 |
| --- | --- | --- | --- |
| 1 | 내가 PRD·story-service·design.md와 실제 작업 방식 문서를 확인한다. 사용자 목표·MVP 범위·고정 원칙·미확정 정책을 구분하고 대표 게시물 링크와 본문을 준비한다. | 입력 자료 목록·요구사항 대응표·정책 질문·미확보 자료 | 기존 카테고리 사용, 근거 없는 설명·URL 생성 금지, 사용자 확인 후 저장, 개인 데이터 보호를 유지한다. 사전 태그 목록 밖의 자동 제안 허용 여부는 별도 정책으로 확인한다. |
| 2 | 내가 uibowl에서 아카이빙·북마크·라이브러리·검색·정보 검토 흐름이 유사한 경쟁사와 인접 서비스의 레퍼런스를 수집한다. | 경쟁사 레퍼런스 수집본·출처·화면 및 행동별 분류 | 수집 자체에는 별도 컨펌을 두지 않는다. 서비스명·출처·참고 화면·수집일을 남기고, 찾지 못한 패턴은 미확보로 기록한다. |
| 3 | 내가 레퍼런스를 분석해 우리 서비스에 반영할 패턴과 제외할 요소를 정리한다. 분석 결과와 적용 방향을 내부 관계자에게 제시한다. | 레퍼런스 분석·반영/제외 목록·근거·검토 의견 | **G1: 분석·반영 방향 확인.** 카드 탐색, 근거 확인, 후보 편집, 분류 방식이 이번 문제를 돕는가? 피드백을 반영하고 방향이 확인된 뒤 화면 설계를 구체화한다. |
| 4 | 내가 확인된 분석을 토대로 화면 설계 문서를 구체화한다. 5개 화면의 정보 위계·사용자 흐름·입력 항목·주요 행동·오류 및 복구 상태를 정의한다. | 화면 설계 문서·사용자 흐름·상태 목록·분류 관리 방식 | 후보 0개·1개·여러 개, URL 누락, 접근 제한, 중복, 부분 저장과 재시도를 포함한다. 서비스 URL과 출처 URL을 구분한다. 사전 태그 관리가 필요한 경우 기존 화면 안의 모드·구역으로 설계한다. |
| 5 | 내가 레퍼런스와 화면 설계서를 반영해 Figma에서 **390×844 키스크린 2~3개**를 만든다. 내 아카이브·추출 결과 확인을 우선하고, 필요하면 링크 추가를 세 번째로 포함한다. | UI 키스크린 2~3개·컨셉 설명·주요 전환·시안 비교 | 이 단계는 모든 화면을 완성하는 단계가 아니다. 검토 정확성과 탐색 속도, 근거 배치, 직접 편집과 펼침 편집의 차이를 검토한다. design.md를 기준으로 만들되 신규 토큰·컴포넌트의 본격 제작은 컨셉 확정 뒤 진행한다. |
| 6 | 내가 내부 관계자들과 화면 설계·키스크린·컨셉을 협의한다. 선택 방향, 수정 요청, 구현 제약과 미확정 사항을 기록하고 필요한 부분을 고친다. | 검토 의견·확정 컨셉 시안·선택 근거·잔여 이슈 | **G2: 화면 설계·키스크린·컨셉 확정.** 확정 전에는 신규 토큰·컴포넌트와 전체 화면 제작으로 넘어가지 않는다. 첨부의 화면 설계 확인과 키스크린 컨펌·컨셉 협의를 하나의 게이트로 묶되 검토 항목은 각각 남긴다. |
| 7 | 내가 확정된 컨셉과 design.md를 기준으로 디자인 토큰과 재사용 컴포넌트를 제작한다. 변경이나 추가가 필요하면 기존 규칙과 영향 범위를 정리한다. | 디자인 토큰·컴포넌트·variant/state·가이드 대응표 | 색·타이포·간격·모서리 규칙을 매핑한다. 서비스 카드·추출 후보·검색·필터·입력·상태 배지의 기본·활성·오류·비활성 상태를 정의한다. 확정 컨셉과 가이드가 충돌하면 규칙 변경을 임의로 처리하지 않는다. |
| 8 | 내가 토큰·컴포넌트로 5개 핵심 화면과 상태별 화면을 제작한다. 키스크린을 전체 흐름으로 확장하고 PC·모바일 반응형을 정리한다. | 전체 화면·상태별 시안·프로토타입·반응형 규칙·콘텐츠 점검 기록 | 390×844를 모바일 기준으로 사용하며 360px과 PC도 PRD 범위에 따라 확인한다. 긴 이름·URL·설명, 로고 없음, 복수 후보, 고정 저장 영역과 키보드 상황을 점검한다. |
| 9 | 내가 완성된 시안의 토큰·컴포넌트·화면을 design.md와 대조한다. 위반 위치와 이유를 기록하고 수정 후 다시 확인한다. | 가이드 검토 결과·위반 목록·수정 기록·통과 결과 | **G3: 가이드 적합성 검토.** 검정 CTA·필 버튼·중립색 표면·그림자 없음·확인 필요용 파란색·정보 위계·접근성을 확인한다. 필수 규칙 위반이 남으면 구현 전달을 보류하고 수정한다. 가이드 예외는 승인 근거를 별도 기록한다. |
| 10 | 내가 검토를 마친 화면과 개발 가이드를 정리하고 구현 조건을 확정한다. 별도 개발자가 참여하면 수집·추출·분류·저장 책임과 데이터 계약을 함께 확인한다. | 최종 디자인·개발 가이드·데이터/API 계약·기술 검증 기록 | 출처 다대다 연결, 후보 단위 중복 저장 방지, 사용자 수정값 보존, 소유권 검증을 확인한다. 링크 수집·추출의 작은 실험은 필요한 정책·설계 단계에서도 수행할 수 있으나 UI 레퍼런스 분석과 별도 결과로 관리한다. |
| 11 | 내가 구현 후 디자인 QA와 PRD 수용 기준 검증을 진행하고 문제를 수정한다. 대표 샘플의 추출 품질과 저장한 서비스의 재탐색을 측정한다. | QA 결과·AC-01~AC-10 검증·수정 목록·잔여 한계 | 선택 저장·URL 누락·수동 대안·중복 출처·검색·편집 반영·부분 저장 재시도·카테고리 삭제·입력 보호·인증을 확인한다. 추출 품질과 시간 지표는 측정 전까지 목표로만 기록한다. |

단계 1은 준비, 2~9는 첨부한 실제 디자인 작업 방식, 10~11은 구현 전달과 검증이다. 내부 관계자 확인은 이 프로젝트에서 진행할 업무 게이트를 뜻하며, 이 문서를 수정하기 위한 추가 승인 요청을 뜻하지 않는다.

| 7 | 토큰·컴포넌트 제작 | 토큰·컴포넌트·상태 정의 | G2 통과 후 진입 | 확정 컨셉·가이드 → 재사용 디자인 자산 |

경계는 다른 도구·문서·사람과 입력 및 결과를 주고받는 지점이다. Figma나 가이드 문서는 사람처럼 승인하는 주체가 아니다. 각 경계를 별도 에이전트로 구현해야 한다는 뜻도 아니다.

## 게이트 정의

| Gate | 위치 | 확인할 입력 | 통과 조건 | 수정이 필요할 때 |
| --- | --- | --- | --- | --- |
| G1 | 레퍼런스 분석 → 화면 설계 | 분석·반영 방향·제외 이유 | 내부 관계자가 적용 방향을 확인하고 미확정 사항을 구분했다 | 레퍼런스 또는 분석을 보완하고 재확인 |
| G2 | 설계·키스크린 → 토큰·컴포넌트·전체 화면 | 화면 설계 문서·390×844 키스크린 2~3개·컨셉 근거 | 내부 협의로 컨셉과 제작 범위를 확정하고 주요 수정 요청을 반영했다 | 화면 설계·키스크린을 수정해 다시 협의 |
| G3 | 완성 시안 → 구현 전달 | 토큰·컴포넌트·전체 화면·design.md | 필수 가이드 위반을 수정하고 검토 결과를 기록했다 | 영향 범위에 따라 토큰·컴포넌트·화면을 고친 뒤 재검토 |

첨부에서 반복된 2번과 2~3 사이의 확인은 G1로 통합했다. 3~6 사이의 확인, 4번 컨펌, 5번 컨셉 확정은 G2로 통합했다. 7번 완성 시안 검토는 G3로 연결했다. 게이트 기록에는 대상 버전·검토자·판단·근거·수정 요청을 남긴다.

## 작업에서 추출한 것

- **행위자:** 나(서비스 사용자·디자이너·프런트엔드 개발자), 내부 관계자, 필요 시 별도 개발 담당자. 관계자의 실제 역할과 승인 범위는 착수 시 정한다.
- **도구:** uibowl, Figma, 코드 에디터, 브라우저·개발자 도구. 수집·모델·저장·인증 도구는 구현 단계에서 선택한다.
- **기준 문서:** PRD, story-service, design.md. 서비스 요구사항은 PRD·story-service, 시각·컴포넌트 규칙은 design.md에 대조한다.
- **작업 대상:** 레퍼런스 수집본, 분석 결과, 서비스 반영 방향, 화면 설계 문서, UI 키스크린 2~3개, 확정 컨셉, 토큰, 컴포넌트, 전체 화면, 가이드 검토 결과, 개발 가이드, QA 결과.
- **판단 지점:** 고정 원칙·미확정 정책(1), 사례 적용 여부(3), 상태별 행동(4), 검토 전략·정보 위계(5), 컨셉 선택(6), 토큰·컴포넌트 규칙(7), 반응형·콘텐츠 대응(8), 가이드 적합성(9), 구현 조건(10), 수용 기준 충족(11).
- **협업 지점:** 레퍼런스 분석과 적용 방향 확인(G1), 화면 설계·키스크린·컨셉 협의(G2), 가이드 예외가 필요한 경우의 결정, 별도 담당자가 참여하는 구현 계약 확인.
- **하네스 후보:** 요구사항 정리, 수집된 레퍼런스의 구조화·비교, 반영/제외 이유 초안, 화면 설계·상태 목록 초안, 키스크린 제작 입력 정리, 검토 의견과 수정 사항 추적, 토큰·컴포넌트 규칙 대조, 개발 가이드·QA 결과 정리.
- **사람이 결정할 것:** 적용 방향·컨셉·가이드 예외·출시 여부. 서비스 이용 중 후보 저장·제외·출처 연결과 미확인 정보 보완도 사용자가 결정한다.

## 서비스 스토리와 작업의 연결

## 이번 수정에서 실제로 한 일

1. 기존 story-work와 첨부한 실제 작업 방식 문서를 확인했다.
2. uibowl 레퍼런스 수집·분석을 분리하고 화면 설계 전 방향 확인을 추가했다.
3. 390×844 키스크린 2~3개와 내부 컨셉 협의를 전체 화면 제작 앞에 배치했다.
4. 컨셉 확정 뒤 토큰·컴포넌트를 제작하고 전체 화면을 확장하는 순서를 반영했다.
5. 완성 시안을 design.md와 대조하는 검토를 독립 단계로 만들었다.
6. 중복 컨펌을 G1~G3로 정리하고 도구·사람·문서의 경계와 입출력을 명시했다.
7. 기존의 서비스 요구사항·예외 상태·구현 및 QA 흐름을 새 작업 순서에 연결했다.
